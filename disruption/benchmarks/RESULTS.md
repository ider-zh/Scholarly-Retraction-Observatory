# 性能评估与执行决策

评估日期：2026-09-23。实测环境：48 逻辑 CPU、755 GiB RAM，评估开始时约
634 GiB available，`/mnt/hg02` 约 5.5 TiB 可用。共享服务器，不占满全部资源。
RTK 未安装，命令使用原生 shell；没有安装 hook 或修改系统配置。

## 已完成：全量文件元数据核对

`inventory.py` 读取 manifest 与全部 2,446 个 Works Parquet footer，核对文件大小、行数。
共 510,372,821 Works；引用列表叶级槽位 3,473,805,571；引用列磁盘压缩大小
31,705,282,401 bytes。槽位包括空列表占位、缺失和重复，**不是规范边数**。
此次检查没有扫描全部引用值，也不是网络闭包或时间质量检查。

若每个 Work 映射到稠密 uint32 编号，双向 CSR 使用 uint32 邻接数组、uint64 offsets，
按上述槽位粗估约 35.96 GB。此数字不包含 ID 映射、元数据、构图暂存和工作线程 scratch。
一个全节点 uint32 scratch 约 2.04 GB，40 个约 81.66 GB；因此不得在每个线程复制整图，
也不得把 Go 的 map/object graph 当作紧凑 CSR 的同等容量估计。

结论：共享不可变压缩索引的内存容量具有可行性；NR 的两跳访问与去重成本仍需实测，
不能用“内存足够”推导全图完成时间。

## 已完成：真实列的压缩试验

从按文件字节数排序的中位分片和最大分片各取前 100,000 行，保存 id、年份、类型、
core/xpac、references 和 primary topic。它不是随机论文样本，也不代表全部字段分布。
PyArrow 23.0.1，所有 codec 均逐表 roundtrip 相等；相同 Parquet 编码设置。

| Codec | 样本一 MB | 样本二 MB | 两份写入秒数之和 |
| --- | ---: | ---: | ---: |
| 无压缩 | 20.05 | 87.67 | 0.343 |
| Snappy | 6.42 | 25.66 | 0.463 |
| ZSTD level 1 | 3.95 | 14.08 | 0.554 |
| ZSTD level 3 | 4.25 | 15.73 | 0.805 |
| ZSTD level 6 | 4.06 | 14.96 | 1.656 |

使用十进制 MB。此次 ZSTD 1 比未压缩 Parquet 小约 80.3% / 83.9%，同时比更高 level
快且更小，选择 **ZSTD level 1** 作为基础缓存默认值，允许版本化调整。
不能假定压缩等级提高一定更小；这里没有把原始嵌套 JSON 大小当基线。
读取为热页缓存、单次测量，未执行 drop_caches，也未测量稳定磁盘带宽或 fsync 延迟。
压缩减少文件读写字节，但不承诺每种负载总耗时都更短。

## 已完成：Go / Rust 共享图并行读取

Go 1.26.0、Rust 1.91.0，优化编译；相同确定性合成图 120,000 节点、1,855,547 边。
24,000 个 focal 查询重复 100 次，共 240 万查询；精确计算不含发表年 5y 的 NF/NB/NR。
三轮交替执行，构图不计入计算耗时；所有运行均匹配独立 Python 集合算法校验和。

| 工作线程 | Go 计算秒数中位数 | Rust 计算秒数中位数 |
| --- | ---: | ---: |
| 1 | 9.535 | 6.324 |
| 8 | 1.175 | 1.131 |
| 40 | 0.350 | 0.593 |

当前决策：**Go 作为后续共享内存图引擎的首选实现语言**，PyArrow/DuckDB 承担压缩列缓存。
这里 Rust 单线程更快，Go 在 40 线程的此实现更快，不存在“某语言一定更快”的结论。
本轮 Go 峰值进程 RSS 约 43.7 MiB、Rust 约 33.1 MiB，不能外推真实大图内存。
工作集小、有重复访问、无磁盘读写、不覆盖真实极端高入度尾部和所有年份；没有测得
全图吞吐率，更不能把 240 万重复查询直接当作 240 万不同论文生产计算。
正式 NR 作业前仍要用完整邻域做真实尾部基准；若不足，调整布局/调度并重新比较。
代码与原始结果见 `run_engine.py`、`graph_read.go`、`graph_read.rs`，以及外部
`engine-20260923/results.json`；这两个内核是基准程序，不是完整生产计算器。

## 工具边界与并发约束

- Parquet 投影、压缩与列转换使用现有 PyArrow/DuckDB 原生执行器，Python 只负责协调，
  不使用 Python 对象保存数十亿边。
- 图计算候选为 Go/Rust 的共享不可变 CSR；线程只拥有独立计数、标记与输出缓冲。
  语言选择以相同算法、校验和和线程数实测为依据，不以“支持并发”作为性能结论。
- CPU 总上限 40，进程数乘每进程线程数不超过上限；RAM 总上限 384 GiB。
  使用用户级 systemd 的 `MemoryMax=384G` 和 `CPUQuota=4000%` 约束长任务。
- 新增磁盘上限 4 TB，并至少保留 1 TB 可用空间。输出、临时文件和索引都计入；
  大文件仅写 `/mnt/hg02/openalex-snapshot/analysis/disruption/`。
- `/mnt/hg02` 本身不能由当前用户创建子目录，改用上述可写位置，不请求提权或修改权限。
- 先完成基础投影缓存并复用，再构建双向索引；未完成的分区不作为零计数。
  合成图性能不能替代真实高入度尾部基准，正式 NF/NB/NR 全图统计仍须通过该关卡。

## 原始证据与复跑

本机证据目录：`/mnt/hg02/openalex-snapshot/analysis/disruption/benchmarks/`。
其中 `inventory-20260923.json`、`compression-20260923/compression.json` 保存输入哈希与实测值。
大样本文件不进 Git。脚本接受显式 `--snapshot` / `--output`，不隐式下载或改写源数据。

工具文档：[Arrow Parquet 压缩](https://arrow.apache.org/docs/python/parquet.html)、
[Go GC 内存限制](https://go.dev/doc/gc-guide)。Go 的 GOMEMLIMIT 是软限制，不能代替
进程树实际内存监测或系统资源上限；Rust 没有 GC 也不代表无需 scratch 内存预算。
