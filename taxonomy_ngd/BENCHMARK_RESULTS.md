# NGD 引擎实测选型

2026-09-25 实测；不是引用图 Disruption 基准的复用结论。
机器 48 个逻辑 CPU；作业上限 40 CPU、384 GiB RAM，不允许 swap。
候选均使用相同 DuckDB 列式解码/标签解析层，相同完整 membership/counts/audit 压缩交付。
Go/Rust 方案包含紧凑整数桥接、进程启动、原生计数、输出写入和文件哈希，不隐去桥接开销。

## 端到端比较

三个冻结真实分片共 904,869 Works，包含 core、xpac、无标签、多标签、最高 39 个 Concept
和 3 个 Topic 的输入。各候选每个分片重复三次，逐项验证原始计数、完整 membership 和 audit 一致。

以下是每一轮三片耗时合计的中位数，不是全库时间预估：

| 路线 | 秒 |
| --- | ---: |
| DuckDB 投影与 SQL 计数 | 112.19 |
| DuckDB 投影 + Go 精确计数 | 64.86 |
| DuckDB 投影 + Rust 精确计数 | 66.95 |

选择 Go 混合方案。Go 与 Rust 相差约 3%，不能据此宣称 Go 普遍快于 Rust。
另有相同已解码输入的内核测量；原始结果保留每次计时、输入规模、阶段耗时、
进程 CPU、实际 I/O 计数、输出字节、worker 进程峰值 RSS 和版本。

## 资源扩展

固定 40 个测试任务、12,163,297 Work 行（重复基准输入，绝不是正式 universe），
比较并发配置：

| workers | 秒 | Works/s |
| ---: | ---: | ---: |
| 1 | 840.56 | 14,470 |
| 8 | 129.68 | 93,794 |
| 16 | 84.91 | 143,257 |
| 32 | 62.02 | 196,117 |
| 40 | 56.02 | 217,140 |

因此正式扫描采用 40 workers。无需为了“用满 RAM”加载整个原始快照，紧凑缓存与有界 worker 足够。
各 worker 的峰值 RSS 约 2.4–2.5 GiB；它不是同时发生的 cgroup 峰值，也不代表全库峰值。
