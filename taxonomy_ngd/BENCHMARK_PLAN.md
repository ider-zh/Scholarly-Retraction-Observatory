# 正式计算前的性能选型门槛

状态：**已执行并选用 Go 混合方案、40 workers**；实测数据与局限见 `BENCHMARK_RESULTS.md`。

## 1. 候选与比较对象

至少评估 Go、Rust 和现有 PyArrow / DuckDB 列式路线。Python 可负责调度和验证，
不能把 Python 逐行循环当作唯一基线，以制造原生语言的虚假优势。
Go/Rust 使用优化生产构建，记录编译器、构建参数、依赖、源码哈希和机器信息。
若工具链或 Parquet 库不可用，记录事实和限制，不自动声称某语言更快。

本任务只需要 Work—分类 membership 的去重和笛卡尔积计数。
输入规模巨大，但输出计数矩阵很小；不构造不必要的 Work×Work 或 citation graph。

## 2. 两层基准

1. **内核基准**：各候选接收同一份规范解码输入，使用同一节点编码，执行精确去重、
   边际/joint 计数和汇总。单独报告解码/桥接成本，不将其隐藏在测试外。
2. **端到端基准**：从相同冻结源分片读取，到生成相同 membership、计数、审计和完整性
   清单结束，包括 Parquet 解码、ID 映射、压缩、落盘和哈希。若采用混合引擎，其桥接时间、
   中间文件和资源也必须计入。

固定 codec、压缩等级及可比的 row-group/batch 设置；允许调优，但记录参数与体积差异。
不能用不写数据的 Go 内核对比写完整 ZSTD 输出的 DuckDB 管道来选生产引擎。

## 3. 样本与正确性先行

- 先通过 ACCEPTANCE 的独立集合 oracle、重复标签、多标签跨父级、空列表和异常测试。
- 冻结真实源分片清单，覆盖 core/xpac、无标签、普通多标签和高标签数输入。
- 小样本验证后扩大到足以暴露内存带宽、压缩和磁盘瓶颈的规模；不能只测合成均匀数据。
- 每个候选须逐项匹配 N、所有边际/joint、membership、异常计数；文件二进制可不同，
  解码后的语义结果必须相同。任何遗漏或近似都不参与性能优胜比较。
- 试验样本不发布成正式矩阵，也不拿样本 NGD 当作全库值。

## 4. 并发与内存测试

在机器实际可用资源和 SPEC 上限内，测试例如 1、8、16、32、40 workers 的扩展曲线。
约束所有进程的总线程数，避免“多进程×多线程”意外超配。测量现有作业负载并避让。

候选优化包括：

- 紧凑整数分类 ID、位集合或小型去重数组，避免每 Work 大量字符串哈希和对象分配。
- 只读共享 taxonomy/membership；每 worker 私有边际与 joint 数组，最终精确归并。
- 有界批次和流水线，分别调整解码、计数、压缩并发，减少批次尾部等待。
- 足够 RAM 下测试投影列缓存或紧凑 membership 缓存，但不要求把全源快照装进内存。
- Go 记录 GC/分配影响，Rust 记录分配与所有权/共享布局；不假设无 GC 必然更快。

所有中间磁盘缓存使用压缩格式；内存内紧凑解码表示不要求压缩。
不要通过系统级清空 page cache 等操作干扰其他作业；区分首次读取与重复读取状态，
不能把未验证的“首次运行”叫作冷缓存测试。

## 5. 记录与选型

各可比配置尽量重复至少三次，保留每次结果和中位数/范围：

```text
输入 Work 数、标签条目数、源压缩字节数
wall time、Works/s、标签条目/s
CPU 时间、实际利用核数、并发扩展效率
峰值 RSS / cgroup 内存（无法取得峰值时标注为采样值）
读取/写入字节、临时磁盘峰值、最终压缩体积
解码、计数、归并、压缩、校验阶段耗时
语义一致性结果、失败/恢复行为
硬件、系统负载、缓存状态、版本和配置哈希
```

先满足精确性、全覆盖、压缩与可恢复性，再以资源限额内端到端吞吐选择。
不能宣称找到了所有可能工具中的绝对最优；只能报告已测候选和参数中的选择。
速度接近时比较内存、磁盘、维护成本和稳定性，不为小幅内核收益迁移整个技术栈。
产出基准报告和冻结运行配置后，才启动全量统计；后续调优不得改变统计语义。
